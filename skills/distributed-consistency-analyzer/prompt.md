# 分散トランザクションの不整合リスク分析スキル

## スキル概要

複数のリソース（ファイルシステム、データベース等）にまたがるトランザクション処理の不整合リスクを体系的に分析し、
リスク評価と対策案を策定するスキルです。

特に、操作の順序変更（例：DB→FS から FS→DB への変更）による影響を包括的に検討します。

---

## 分析手順

### 1. システム構成の理解

入力されたシステム構成を確認し、以下を把握せよ：
- 対象システムの概要
- 操作の対象リソース（DB、FS、キャッシュ等）
- 各操作の役割と依存関係

### 2. 分析対象の特定

検討対象の操作順序を明確にせよ：

#### パターンA: 現状（例：DB→FS）
1. データベース操作（INSERT/UPDATE）
2. トランザクション確定（commit）
3. ファイルシステム操作（move/create）

**失敗シナリオ**：commit成功後、FS操作失敗
→ 結果：DBあり、FSなし（DB側が真実を持つが、物理的に矛盾）

#### パターンB: 提案（例：FS→DB）
1. ファイルシステム操作（move/create）
2. データベース操作（INSERT/UPDATE）
3. トランザクション確定（commit）

**失敗シナリオ**：FS成功後、DB操作失敗
→ 結果：FSあり、DBなし（物理ファイルが存在するが、DBに未記録）

### 3. 不整合パターンの検討

各操作順序について、以下のケースを検討せよ：

#### ケース1: 最初の操作成功 → 後続操作失敗

**パターンA（DB→FS）の場合**：
- DB処理が成功し commit() も確定した後、FS操作（shutil.move等）が失敗
- 失敗トリガー例：
  * パーミッション不足
  * ストレージ満杯
  * ファイルシステムエラー
  * 別プロセスでファイルロック中

**パターンB（FS→DB）の場合**：
- FS操作は成功したが、DB操作（INSERT）や commit() が失敗
- 失敗トリガー例：
  * UNIQUE制約違反
  * ディスク満杯（DB側）
  * データベース破損
  * メモリ不足

**分析ポイント**：
- 結果状態は何か（どちらのリソースに不整合が生じるか）
- ユーザーにはどう見えるか（エラーか無言の失敗か）
- 検出は容易か（ログに明記されるか、無視されるか）
- 復旧は容易か（再度アップロード等で復旧するか、手動対応が必要か）

#### ケース2: 複数DB/テーブル間の不整合

複数のテーブルに操作がまたがる場合：
- テーブルA は INSERT 成功
- テーブルB は INSERT 失敗（もしくはスキップ）
- トランザクション内で途中まで成功した状態

例：
- rag_source_files テーブルに INSERT 成功
- document_chunks テーブルに INSERT 失敗
- 結果：メタデータは存在するが、検索用チャンクがない

**分析ポイント**：
- テーブル間の依存関係
- 部分的な登録状態の影響
- 検出困難性

#### ケース3: ロールバック失敗

エラーハンドリング時のロールバック処理自体が失敗するケース：
- 最初の操作は成功（FS移動等）
- DB操作失敗 → ロールバック試行
- ロールバック処理（例：FS削除）自体が失敗
- 結果：ファイルが削除されずに残存

**失敗トリガー**：
- 削除対象ファイルが他プロセスで開かれている
- パーミッション不足
- ファイルシステムエラー
- 削除ロジックのバグ

**分析ポイント**：
- ロールバック処理の堅牢性
- 削除失敗時の代替手段
- ゴミファイルの蓄積リスク

### 4. 現状との比較表作成

以下の項目で両パターンを比較せよ：

| 項目 | パターンA（現状） | パターンB（提案） |
|------|-----------------|-----------------|
| **不整合パターン** | DBあり・FSなし | FSあり・DBなし |
| **発生トリガー** | FS操作失敗 | DB操作失敗 |
| **ユーザーへの影響** | エラーとして認識 | 無言の失敗（検出困難） |
| **検出容易性** | 高（ログに明記） | 低（孤立ファイルは目立たない） |
| **復旧容易性** | 低（ファイル再取得必要） | 中（ファイルは残存） |
| **発生確率** | 中（FS操作は複雑） | 低（DB操作は単純） |
| **ユーザー体験** | すぐエラー表示 | 何も起きない |
| **ロールバック複雑度** | 単純 | 複雑（FS削除も） |

**追加観点**：
- スクリプト堅牢性
- 蓄積コスト（無駄なファイル・レコードの蓄積）
- 監視容易性（エラーログの有無）

### 5. 推奨事項の策定

複数の戦略案を検討し、各案をメリット・デメリットで評価せよ：

#### 戦略1：パターンBを単体採用

**メリット**：
- DB操作失敗（INSERTやcommit）は相対的に少ないため、問題が生じやすい
- FS操作失敗（頻繁に発生）よりも安全性が高い可能性

**デメリット**：
- 孤立ファイル検出困難（後付け必須）
- ロールバック処理の堅牢性が不確実
- 不整合発生時のデバッグが困難

**評価**：❌ 単体では不十分

#### 戦略2：パターンB + 追加対策

**追加対策A：ロールバック処理の強化**
- DB失敗時のファイル削除ロジックを実装
- 削除失敗の詳細ログを記録（ERROR レベル）
- 削除失敗時の自動リトライ

**追加対策B：孤立ファイル検出・クリーンアップ**
- 定期的に（例：daily 02:00）バッチ処理を実行
- ストレージのファイル一覧と DB レコード一覧を比較
- DB に未登録のファイルを検出・削除

**追加対策C：トランザクション分離（オプション）**
- FS移動（トランザクション外）→ DB登録（トランザクション内）
- Compensating Transactions パターンを採用

**評価**：✅ 推奨策。検出・復旧・防止がバランスよく実装できる

#### 戦略3：現状維持 + 簡易クリーンアップ

**説明**：
- パターンA（DB→FS）を維持
- 定期的なクリーンアップを追加して孤立ファイルを削除

**メリット**：
- 現行コードの変更が最小限
- リスク低（既知のパターン）

**デメリット**：
- 引き続き「DB成功→FS失敗」の不整合が発生
- 監視・ロギング強化が必要

**評価**：△ 消極的だが、短期は許容可能

#### その他の組み合わせ

必要に応じてカスタマイズした戦略を検討

### 6. 最終推奨の作成

以下を明記した最終推奨を策定せよ：
- **選択戦略**：複数案の中から最適な1つを選択
- **理由**：
  * 発生確率の比較
  * ユーザー体験への影響
  * 復旧容易性
  * 監視・保守コスト
- **アクションアイテム**：
  1. コード実装（何を変更するか）
  2. ロールバック処理の強化（削除失敗時の対応）
  3. 定期クリーンアップタスク設計
  4. テスト実装（失敗シミュレーション）
  5. ドキュメント更新

## 使用例

### 例1：FS→DB順序への変更検討

**入力**：
- system_description: "Flask+SQLite RAG ドキュメント登録システム"
- operation_sequence: "FS → DB"
- operations:
  * shutil.move(temp, storage)
  * INSERT rag_source_files
  * commit()
- current_sequence: "DB → FS"

**出力**：
- 3つの不整合ケース分析
- 現状との詳細比較
- 4つの戦略評価
- 推奨：FS→DB + ロールバック強化 + 定期クリーンアップ
- 5つのアクションアイテム

---

## 注意事項

1. **完全性への幻想を持つな**
   - どちらの順序でも完全な安全性はない
   - 不整合発生のリスクは常に存在

2. **定期的な監視が必須**
   - 孤立ファイル・孤立レコードの検出
   - エラーログの定期確認

3. **組織のリスク許容度に応じたカスタマイズ**
   - セキュリティ優先：完全性重視
   - UX優先：検出容易性重視
   - パフォーマンス優先：操作順序最適化

4. **修正後の再評価**
   - 実装後に必ず再度検証
   - 新たな問題の確認
   - ドキュメント更新
